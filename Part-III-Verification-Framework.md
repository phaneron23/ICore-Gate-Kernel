# ICore.Gate — Minimal Constitutional Kernel v1.0

## Part III — Constitutional Verification Framework

Every proposal must pass all 10 tests before becoming constitutional.
One failure = rejection. No exceptions.

---

### The Tests

| # | Test | Question | Pass Criterion |
|---|------|----------|----------------|
| 1 | **Reality** | Does this correspond to something real? | The proposal references a verifiable reality, not a hypothetical or invented construct. |
| 2 | **Origin** | Can its source be traced? | Every claim cites its derivation source — USCP, USC, or a verified higher layer. No orphaned assertions. |
| 3 | **Constitutional Necessity** | Must this exist at the constitutional level? | Removing it would break the kernel or leave a verifiable gap. If it can live in UCD or below, it does not belong in the kernel. |
| 4 | **Derivation** | Is it derived from the layer below? | It follows D1–D5 from Part II. No upward mutations, no skipped layers, no unlicensed merges. |
| 5 | **Consistency** | Does it contradict existing constitutional knowledge? | No logical, structural, or semantic conflict with any previously ratified element. |
| 6 | **Verification** | Can its truth be independently confirmed? | A second party, using only the constitutional stack, can reproduce or verify the claim. |
| 7 | **Simplicity** | Can it be stated more simply? | The proposal is the minimal expression of its purpose. No redundant terms, no unnecessary abstractions. |
| 8 | **Sovereignty** | Does it preserve constitutional independence? | It introduces no external dependency that cannot be replaced through UCA. |
| 9 | **Replaceability** | Can any part of it be swapped without breaking the kernel? | External implementations it references are interface-bounded, not hardwired. |
| 10 | **Evolution** | Can it be amended or retired without destroying what depends on it? | Changes propagate downward through governance. Removal leaves a clean gap, not a cascade failure. |

---

### Application Protocol

**Step 1 — Self-audit.** The proposer applies all 10 tests and records pass/fail with evidence.

**Step 2 — Review.** A second party replicates the audit. Disagreements are resolved by returning to the derivation graph (Part II) — if the graph supports it, the test passes.

**Step 3 — Gate decision.**
- 10/10 pass → ratified, enters constitutional publication.
- 9/10 pass → conditional: the failed test must be remediated within one governance cycle.
- ≤8/10 pass → rejected: re-derivation required from the failed layer downward.

**Step 4 — Record.** Every test result is archived with the proposal. Verification is not a gate — it is a permanent constitutional artifact.

---

### Test Ordering

Tests are ordered by constitutional priority. If a proposal fails Test 1 (Reality), there is no need to run Tests 2–10. This preserves the doctrine: Reality before abstraction.

---

*These 10 tests are the constitutional immune system. They protect the kernel from unverified, unnecessary, or destructive additions.*
